Idempotency guarantee: Each stage writes a checkpoint JSON on completion. A subsequent run skips completed stages unless forced — making the pipeline safe to re-invoke after partial failures without duplicating API calls.

CLI Control Flags

--force

Ignore all checkpoints. Full re-run from scratch.

--from=<stage>

Restart from a specific stage onward. Earlier stages skipped.

--only=<stage>

Run exactly one stage regardless of checkpoint state.

--sections=ai_news

Scope research + generate to named sections. Validate skipped automatically.

Injected Components

_RANK_RULE + _URL_RULE merged at generation time

↓ composed into prompt at runtime

RAG context block + section.prompt + _RANK_RULE + _URL_RULE → LLM(model) → JSON.parse()

_RANK_RULE

10–15 smart cutoff: extend past 10 only when adoption clusters tightly within ~25%. Stop at the first significant drop-off. Never pad to fill 15.

_URL_RULE

Official domain only. No comparison sites (g2.com, capterra.com). If the official URL cannot be identified from research data, omit the item entirely.

Why different companies?

Claude and GPT-4o have different training corpora and RLHF signals. Using two Anthropic models produces correlated outputs. Cross-company disagreements represent genuinely conflicting evidence — more useful signal to the end user.

Fallback promotion

If Opus 4.8 fails (timeout, empty response, parse error), the Critic's output is automatically promoted to primary. For ai_news, Sonnet 4.6 is the secondary fallback. All events are logged.

9 Reliability Patterns

Defense-in-depth: pipeline never hard-fails, content is always available

🔁

Idempotent Pipeline

Checkpoint files prevent re-running completed stages on failure recovery. Safe to re-invoke at any point without duplicating API calls or corrupting state.

🎯

Partial Refresh

--sections=ai_news scopes research + generate to named sections. Validate stage is automatically skipped — reduces daily news run to ~1 LLM call + 6 search queries.

🗂️

URL Override Registry

url_overrides.json: permanent fixes and false-positive skips applied every run. Auto-fixer only replaces truly broken (404) URLs — wrong-page judgments are reported, not auto-fixed.

🔒

Domain Whitelist

include.json: auto-fixer replacement candidates must come from trusted domains. Any unlisted domain is rejected — no blocklist maintenance required.

🛡️

Zero-Overwrite Guard

ai_news.json is never overwritten if generation returns 0 items. Existing content survives bad runs. Site remains usable even if news research fails.

💾

Content Persistence

All generated JSON is committed to the repo. GitHub Pages serves committed files — the site stays live even if Anthropic or OpenAI APIs go down indefinitely.

12 Design Methodology & Lessons Learned

Spec-driven design, research-first vs iterative, and what we'd do differently

Spec-Driven Design for AI Systems

In traditional software, you write a function signature first — the contract — then implement it, then test against the contract. Spec-driven design applies the same discipline to LLM-based systems: define the output contract before writing any prompt. The spec becomes both the prompt instruction and the test oracle.

The core discipline

The spec must be complete enough to be wrong. A vague spec ("list some tools") produces unverifiable output. A precise spec (rank: integer 1–15, url: official domain only, monthly_active_users: string with source) creates a machine-checkable contract. The LLM is the implementation; the spec is the interface. If generation fails parse or validation, the spec reveals the gap — not the model.

Research-First vs Iterative Generation

There are two fundamentally different approaches to grounding AI-generated content. This project uses research-first. Understanding the tradeoff is important when designing similar pipelines.

THIS PROJECT

Research-First (RAG)

1. Retrieve live context before any generation call
2. Inject context into prompt as a grounding block
3. Generate once against full context
4. Validate output — no re-generation loop

✅ Predictable cost — 1 LLM call per section

✅ Deterministic — same context → same output

✅ Fast — all sections run in parallel

⚠️ Research quality sets the ceiling

⚠️ One shot — no self-correction

ALTERNATIVE

Iterative (Agentic Loop)

1. Generate a draft from base knowledge
2. Evaluate draft — identify gaps, check facts
3. Search to fill specific gaps found in step 2
4. Refine draft with new evidence → loop until pass

✅ Self-correcting — catches its own gaps

✅ Higher ceiling for complex reasoning

⚠️ Variable cost — loop count unpredictable

⚠️ Harder to parallelize across sections

⚠️ Requires exit condition to avoid runaway loops

When to use each

Research-first works best when:

  • • Output schema is fixed and machine-verifiable
  • • You run many parallel sections (cost compounds fast in loops)
  • • Content ages quickly — freshness comes from retrieval, not reasoning
  • • Deterministic per-run cost matters (scheduled jobs, CI/CD)

Iterative works best when:

  • • The question is open-ended or exploratory
  • • Output quality depends on chasing down specific evidence
  • • A single retrieval pass may surface the wrong context
  • • Cost per run is bounded by a hard max-steps limit

What We'd Do Differently

Honest retrospective — things that emerged organically but should have been designed upfront.

📋

Formal JSON Schema from day one

Each section's prompt defines the output shape in prose. We should have written a schemas/{key}.json JSON Schema file first and auto-generated the prompt from it. That way validation is mechanical (jsonschema library) rather than "try to parse it and see." Schema-first also makes adding new sections faster — the template, validator, and prompt all derive from one source of truth.

Better: schema → prompt (generated) → output → validate(schema)

🔗

URL validation built into the generation spec, not a separate stage

URL validation grew into its own pipeline stage with an override registry, whitelist file, and manual triage workflow. The cleaner design: include domain constraints in the spec itself (url must resolve to official vendor page), run a lightweight HTTP check immediately after each section generates, and reject+retry rather than accumulating a fix registry. The url_overrides.json file exists because generation wasn't strict enough upfront.

🧪

Automated regression tests for content quality

Right now there's no automated check that says "did this run produce worse output than last run?" We catch structural failures (parse errors, broken URLs) but not semantic regressions (a section dropping from 10 items to 3, a tool appearing that doesn't match the section's domain, a ranking that looks implausible). A simple diff-based alert on item count ± key fields after each generation run would catch silent degradation early.

Add: compare content/{key}.json to previous version — alert on item count drop > 30%

🔍

Research queries should have been evaluated independently

Research queries were written alongside section specs without measuring their actual retrieval quality. A better approach: before writing the generation prompt, run the queries and read the results — check whether they return relevant, current content. Poor research context is the most common cause of stale or hallucinated output, and it's invisible once generation runs. Query quality should be a first-class design concern.

💰

Cost model should have driven the schedule from day one

The project launched with weekly full refresh. We only analyzed the cost tradeoff later and switched to monthly full + daily news — a 56% cost reduction. The right question to ask first: "How often does each section's content actually change?" Tool rankings change slowly (monthly). News changes daily. These have different optimal cadences and should have been in separate workflows from the start.

Rule: define refresh cadence per content type before writing the cron schedule

📐

config.json should have been the starting point, not a retrofit

Site identity (title, author, branding) was initially hardcoded in multiple templates and scripts. config.json was added later as a centralisation fix. Any project with more than one output artifact (dashboard, news page, standalone, about page) should start with a single config file that all build scripts read. The pattern is free — the cost is only paid when you don't do it and have to touch six files to change a name.
