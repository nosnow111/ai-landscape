Multi-Agent Pipeline Architecture

An automated agentic pipeline that produces a live AI ecosystem intelligence dashboard. Spec-driven generation, RAG-grounded content, dual-model cross-validation, and checkpoint-based orchestration — served free on GitHub Pages.

1 System Overview

What this system is and what problem it solves

Problem

The AI ecosystem changes faster than any human can manually track. Tool rankings, model pricing, and emerging trends become stale within days.

Solution

An automated multi-agent pipeline that researches, generates, validates, and publishes structured AI ecosystem intelligence on a recurring schedule.

Output

18-section static dashboard (GitHub Pages) with ranked tools, model comparisons, pricing tables, and daily news — zero ops overhead.

# High-level data flow

Web Sources → Retrieval Agents → Context Blocks

→ Generation Agents (Opus 4.8 + GPT-4o) → Structured JSON

→ Validation Agent (Haiku judge) → Verified Artifacts

→ Build Agent (Jinja2) → Static HTML

→ GitHub Actions → GitHub Pages (live)

CLI Control Flags

--force

Ignore all checkpoints. Full re-run from scratch.

--from=<stage>

Restart from a specific stage onward. Earlier stages skipped.

--only=<stage>

Run exactly one stage regardless of checkpoint state.

--sections=ai_news

Scope research + generate to named sections only. Validate skipped automatically.

Idempotency guarantee: Each stage writes a checkpoint JSON on completion. A subsequent run will skip completed stages unless forced — making the pipeline safe to re-invoke after partial failures.

3 Agent Architecture

Six specialized agents with distinct roles, models, and scopes

Agent File Model Role
Orchestrator pipeline.py — (control logic) Stage routing, checkpoint management, CLI interface, fallback promotion
Retrieval Worker research.py — (API calls) Web search per section, context assembly, provider fallback chain
Generation Agent generator.py claude-opus-4-8 Primary content generation against section spec; outputs structured JSON
Critic Agent generator.py gpt-4o Independent cross-check on all ranked sections; agreement annotation
Validation Agent validate_links.py claude-haiku-4-5 LLM-as-judge: fetches each URL, assesses page relevance vs. expected product
Build Agent build.py — (template engine) Jinja2 rendering of content JSON → static HTML; vendor news cache logic

# Agent coordination pattern for each ranked section

Orchestrator dispatches section key to ThreadPoolExecutor(max_workers=18)

└─ per section: ThreadPoolExecutor(max_workers=2)

├─ GenerationAgent(opus-4.8) ← primary

└─ CriticAgent(gpt-4o) ← parallel cross-check

└─ annotate_agreement() reconciles ranks → annotated JSON artifact

└─ saved immediately via as_completed() (no batch wait)

4 Spec-Driven Content Generation

Section prompt specs as typed contracts — the LLM is the implementation

Each of the 18 content sections has a formal prompt specification defined in generator.py:SECTIONS. These specs are structured contracts — analogous to function signatures in typed languages — that fully define expected behavior without prescribing internal reasoning steps.

Every spec defines

  • • Ranking criteria — adoption signals (API volume, surveys, GitHub stars, enterprise deployment)
  • • Output schema — strict JSON structure with named, typed fields
  • • Domain constraints — what to include, exclude, or weight differently
  • • Injected components — reusable rules merged at generation time

Reusable spec components

_RANK_RULE

10–15 smart cutoff: extend past 10 only when adoption clusters, stop at natural drop-off. Never pad.

_URL_RULE

Official domain only. No comparison sites (g2.com, capterra.com). Omit item if URL unverifiable.

SECTIONS = {

"ai_assistants": {

"title": "AI Assistants & Chatbots",

"prompt": (

"Rank top 10 by monthly active users. " # ranking criterion

"Return JSON: {summary, tools: [{name, vendor, rank, "

" monthly_active_users, platforms, strengths, url}]}" # output schema

+ _RANK_RULE + _URL_RULE # injected components

)

}

6 Multi-Agent Cross-Validation Pattern

Primary + Critic with agreement annotation — disagreements are meaningful signals

# Cross-validation flow for ranked sections

GenerationAgent(opus-4.8) ──────────────────────┐

receives: spec + RAG context │

outputs: ranked JSON {tools: [{rank:1, name:...}]} │

▼

CriticAgent(gpt-4o) ──────────────────► annotate_agreement()

receives: same spec + same RAG context │

outputs: independent ranked JSON │

▼

per-item annotation:

strong = exact rank match

minor = ≤2 positions apart

disagree = 3+ positions apart

excluded = critic omitted item

Why different companies?

Claude and GPT-4o have different training data, different pretraining corpora, and different RLHF fine-tuning signals. Using two Anthropic models would produce correlated outputs. Cross-company disagreements represent genuinely conflicting signals — more useful to the end user.

Fallback promotion

If Opus 4.8 fails (timeout, empty response, parse error), the Critic's output is automatically promoted to primary. For ai_news, Sonnet 4.6 is the secondary fallback if Opus fails. All fallback events are logged.

9 Reliability Patterns

Defense-in-depth: pipeline never hard-fails, content is always available

Idempotent Pipeline

Checkpoint files prevent re-running completed stages on failure recovery. Safe to re-invoke at any point without duplicating work or corrupting state.

Partial Refresh

--sections=ai_news scopes research + generate to named sections. Validate stage is automatically skipped — reduces daily news run to ~1 LLM call + 6 search queries.

URL Override Registry

url_overrides.json: permanent fixes and false-positive skips applied every run. Auto-fixer only replaces truly broken (404) URLs — wrong-page judgments are reported, not auto-fixed.

Domain Whitelist

include.json: auto-fixer replacement candidates must come from trusted domains. Any unlisted domain is rejected — no blocklist maintenance required.

Zero-Overwrite Guard

ai_news.json is never overwritten if generation returns 0 items. Existing content survives bad runs. Site remains usable even if news research fails.

Content Persistence

All generated JSON is committed to the repo. GitHub Pages serves committed files — the site stays live even if Anthropic or OpenAI APIs go down indefinitely.

11 Deployment Architecture

Zero-ops static hosting with automated CI/CD via GitHub Actions

# GitHub Actions workflow (refresh.yml)

on: schedule (cron) | workflow_dispatch

steps:

1. checkout@v4 + setup-python@v5 + pip install

2. python pipeline.py [--force | --sections=ai_news --force]

3. git stash # protect generated files

4. git pull --rebase # sync with any concurrent pushes

5. git stash pop

6. python build.py # rebuild with latest template

7. git add content/ docs/ validation_report.json

8. git commit + git push # content committed to main

GitHub Pages serves docs/ from main → live site auto-updated

Why static?

No server = free hosting forever on GitHub Pages. No uptime management, no containers, no cold starts. Content JSON committed to repo — site survives API outages.

config.json

Centralizes site identity (title, author, tagline, about URL). All build scripts load it; template uses {{ config.* }}. Single-file branding changes.

Standalone build

build_standalone.py generates a single self-contained HTML file — Tailwind inlined, all content embedded. Safe to email or share behind firewalls.
