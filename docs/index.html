AI in Major Databases

Modern databases and data platforms have rapidly evolved to embed AI and ML capabilities natively, eliminating the need for complex external pipelines by bringing inference, vector search, and LLM integration directly into the data layer. By 2026, 75% of enterprise AI applications are expected to depend on vector search capabilities, driving platforms like Snowflake, BigQuery, and PostgreSQL to deeply integrate embedding generation, semantic search, and large language model orchestration. The competitive landscape is shifting toward general-purpose data platforms that can serve both transactional and AI workloads, narrowing the gap with purpose-built vector databases.

Snowflake

Vector Search

Cortex AI

🔗 https://www.snowflake.com/en/data-cloud/cortex/

Snowflake Cortex AI provides a suite of fully managed ML and LLM functions running natively inside the Snowflake AI Data Cloud. It includes Cortex LLM Functions (COMPLETE, SUMMARIZE, SENTIMENT, TRANSLATE, EXTRACT_ANSWER) that call hosted LLMs directly via SQL, Cortex Search for hybrid vector and keyword search, Cortex Analyst for natural language to SQL querying, and Cortex Fine-tuning for customizing LLMs on proprietary data. With the general availability of Snowflake Postgres and pgvector integration, Snowflake now also supports native vector similarity search within its Postgres-compatible layer, eliminating ETL complexity and unifying transactional and analytical AI workloads through Unistore.

LLM Integration: Native hosted LLMs including Mistral, Llama 3, Reka, and Arctic models accessible via SQL functions; supports Cortex Search for retrieval-augmented generation (RAG) pipelines and integrates with external models via Snowpark Container Services

Cortex AI functions are billed in Snowflake credits per token processed; costs vary by model size and function type. Cortex Search has separate compute pricing. Snowflake Postgres is generally available soon with pricing expected to follow standard Snowflake compute and storage model. Overall costs can escalate at scale and should be monitored via resource monitors.

Google BigQuery

Vector Search

BigQuery ML + Vertex AI Integration

🔗 https://cloud.google.com/bigquery/docs/bqml-introduction

BigQuery ML enables data teams to build and execute ML models using standard SQL directly inside BigQuery, supporting model types including linear regression, logistic regression, k-means clustering, matrix factorization, boosted trees, deep neural networks, and AutoML. BigQuery's Vertex AI integration allows calling hosted foundation models and custom Vertex AI endpoints via the ML.GENERATE_TEXT and ML.EMBED_TEXT SQL functions, enabling LLM-powered transformations, summarization, classification, and embedding generation at scale without data movement. BigQuery also supports vector search natively via the VECTOR_SEARCH SQL function and stores embeddings as ARRAY columns.

LLM Integration: Deep integration with Google Vertex AI Model Garden; supports Gemini models, PaLM 2, and custom-deployed models via ML.GENERATE_TEXT and ML.EMBED_TEXT SQL functions; enables RAG pipelines entirely within SQL

BigQuery ML model training incurs additional charges beyond standard BigQuery compute. ML.GENERATE_TEXT and ML.EMBED_TEXT calls are billed per character or per 1,000 characters depending on the model. VECTOR_SEARCH queries are billed as standard BigQuery on-demand or flat-rate compute. Vertex AI models used through BigQuery are billed at Vertex AI pricing rates.

PostgreSQL

Vector Search

pgvector + pgai

🔗 https://github.com/pgvector/pgvector

pgvector is a PostgreSQL extension that adds vector similarity search capabilities directly to any PostgreSQL instance, supporting storage and querying of vector embeddings using L2 distance, cosine similarity, and inner product operators. It supports approximate nearest neighbor search via HNSW and IVFFlat indexes, making it suitable for RAG pipelines, semantic search, and recommendation systems without introducing new infrastructure. pgai is a complementary extension developed by Timescale that brings LLM functions into PostgreSQL, enabling embedding generation and LLM inference via SQL calls to providers like OpenAI, Ollama, and Anthropic. Together they represent the lowest-friction path to AI capabilities for organizations already running PostgreSQL, reusing existing security models, backup procedures, and operational tooling. Snowflake Postgres now also runs pgvector natively in the AI Data Cloud.

LLM Integration: pgai extension enables SQL-level calls to OpenAI, Anthropic, Ollama, and other LLM providers for embedding generation and text completion; integrates with LangChain and LlamaIndex for full RAG pipeline construction

pgvector and pgai are open source and free to use on self-hosted PostgreSQL. Managed offerings such as Amazon RDS for PostgreSQL, Google Cloud SQL, Azure Database for PostgreSQL, Supabase, and Timescale Cloud include pgvector support with costs determined by the managed service compute and storage pricing. LLM API calls made via pgai are billed by the respective provider at their standard rates.

Amazon (Aurora ML + Redshift ML)

Vector Search

Aurora ML + Redshift ML

🔗 https://aws.amazon.com/rds/aurora/machine-learning/

Amazon Aurora ML integrates Amazon SageMaker and Amazon Bedrock directly into Aurora MySQL-Compatible and Aurora PostgreSQL-Compatible databases, allowing developers to invoke ML models and foundation LLMs via SQL functions without moving data out of the database. Aurora PostgreSQL also supports pgvector for native vector similarity search. Amazon Redshift ML enables data analysts and engineers to create, train, and deploy ML models using SQL by leveraging Amazon SageMaker AutoPilot under the hood, supporting classification, regression, and clustering use cases. Redshift additionally integrates with Amazon Bedrock for LLM inference via the ML_PREDICT function, enabling embedding generation and text generation directly from SQL queries on data warehouse tables.

LLM Integration: Integration with Amazon Bedrock provides access to foundation models including Amazon Titan, Anthropic Claude, Meta Llama, Mistral, and Cohere via SQL in both Aurora and Redshift; SageMaker endpoints can also be invoked directly from SQL

Aurora ML and Redshift ML charges include the underlying SageMaker or Bedrock API call costs in addition to standard Aurora or Redshift compute and storage pricing. Bedrock model invocations are billed per input and output token at model-specific rates. pgvector on Aurora PostgreSQL has no additional cost beyond the Aurora instance. Data transfer costs may apply when invoking external SageMaker endpoints.

Databricks

Vector Search

MLflow + DBRX + Mosaic AI

🔗 https://www.databricks.com/product/machine-learning

Databricks provides an end-to-end AI and ML platform centered on Mosaic AI, which encompasses MLflow for experiment tracking, model registry, and deployment; DBRX as Databricks' own open high-performance LLM; Vector Search for managed vector database capabilities built natively into the Databricks lakehouse; and AI Playground for interactive LLM experimentation. AI observability matters because LLM applications introduce unique failure modes—hallucinations, prompt drift, latency spikes, and runaway token costs—that traditional APM tools cannot detect. As the LLM observability platform market grows from $2.69 billion in 2026 toward $9.26 billion by 2030 at a 36.2% CAGR, teams need dedicated tooling to trace every prompt and completion, evaluate output quality, and attribute spend to specific users or features. Gartner predicts LLM observability investments will account for 50% of GenAI deployments by 2028, up from 15% in early 2026, making early adoption a competitive advantage.

💡 Cost Reduction Tips

  • •Implement prompt caching aggressively: tools like Helicone expose cache hit rates across 300+ models, and enabling semantic or exact-match caching on repeated or near-identical prompts can reduce token spend by 40-70% on high-volume applications without degrading response quality
  • •Set per-user and per-feature budget guardrails before you scale: use observability tools to attribute cost by user ID, team, or product feature from day one, then configure hard limits and alerts so a single misbehaving agent or a spike in user traffic cannot generate unbounded API spend
  • •Right-size your model selection with trace data: use evaluation frameworks like Langfuse or LangSmith to benchmark smaller, cheaper models against your actual production prompts and quality thresholds—many tasks that teams default to GPT-4-class models can be handled at a fraction of the cost by smaller models with minimal quality loss
  • •Audit and compress prompt templates regularly: long system prompts with redundant instructions are one of the largest hidden cost drivers; use prompt versioning in LangSmith or Langfuse to A/B test trimmed prompt variants, and monitor token counts per trace to catch prompt bloat before it compounds across millions of requests
